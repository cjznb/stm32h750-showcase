# 与 AI 协作的工程方法

> 这是一个**一个人 + AI 工具链**完成的项目。这一页讲方法，不是为了炫工具，而是因为
> **"AI 时代的工程师"真正稀缺的技能是：让 AI 的输出可被验证、可被追溯、可被推翻。**

---

## 1. 分工形态的四步演进

| 阶段 | 形态 | 为什么升级 |
|---|---|---|
| 早期 | **角色扮演**：把工作拆成"UI 绘制者 / 代码编写者"，约定控件命名与交接格式 | 一个会话里上下文互相稀释 |
| 中期 | **项目审计 + 域修复子代理**：先并行审计（构建/驱动/服务/UI/子仓），再按域分派修复 | "先调研再改"，避免边猜边改 |
| 后期 | **加"评审"这一环**：每项任务 = 实现 → **评审（规范 + 质量）** → 修复 → 复审；收口再做四类独立审计（计划符合性 / 代码质量 / 手工 QA / **范围保真**） | 实现者给自己打分不可信 |
| 成熟 | **阶段式批派 + 文件领地切死**：一批任务固定写域边界，主控只做"编排 + 收口验证 + 提交" | 多写者并发时，冲突成本远高于并行收益 |

> **"范围保真"审计**是最有用的一类：专门查"AI 声称做完了、其实只做了一半"或"顺手改了不该改的地方"。

## 2. 任务书怎么写（这套模板沿用至今）

一份可执行的任务书 = **五节 + 四条硬约束**：

```
## 1. TASK            一句话目标
## 2. EXPECTED OUTCOME 验收标准（写成可判定的量，能到寄存器字段级就写到字段级）
## 3. REQUIRED TOOLS   允许改哪些目录 / 用哪个隔离构建目录 / 必须跑哪些命令
## 4. MUST DO          必须交回什么（改动清单 + diff 摘要 + 构建结果 + 上板步骤与预期现象）
## 5. MUST NOT DO      禁止事项（不提交、不改几何、不改某常量、无证据不动某模块…）
```

四条硬约束（每次都写）：

1. **写域边界**：能改哪些文件，别的别碰；
2. **判据串**：验收看哪一行日志/哪个计数；
3. **回退开关**：随时能切回旧行为做 A/B；
4. **禁止事项**：尤其是"不要动别人的模块"和"不要为了通过而改判据"。

## 3. 让结论"可被证伪"的四件套

| 手段 | 具体做法 | 实例 |
|---|---|---|
| **真机 A/B 双臂** | 单变量、两臂都能编、**结果两侧都有数** | SD 写策略：改前 timeouts/reinits 3/3，改后 0/0，吞吐不变 |
| **跨项目/跨配置对照** | 同一硬件换平台/换配置比 | 同一张 SD 卡在旧项目正常 ⇒ 一算发现是**新平台没发 CMD6 就跑到 50 MHz**（超速 2×） |
| **独立审计** | 换一个"只挑错"的角色重新核对 | 查出一份栈深报告的三类系统性错误，整份作废重做 |
| **仿真 + 真机双层** | 仿真跑逻辑、真机跑时序；并**明确写下仿真覆盖不到什么** | 仿真测不到"持文件锁打日志 × 日志 sink 调文件系统"的**双向死锁**（仿真没开文件 sink） |

配套的**纪律清单**（每条都来自一次实际的坑）：

- 改代码前先读现有实现与注释（注释里往往写着"为什么这么写"）；
- 涉及烧录/复位/接线等硬件操作，先问人再动；
- 改动必须**双配置编译**（`Debug` + `RelWithDebInfo`，仿真改动加仿真档）；
- 仿真专用宏**只允许**出现在 CMake / `*_sim.c` / IDE 配置里（CI 守卫强制）；
- **先方案、后执行**（没方案的改动直接冻结该模块）；
- 小步提交、不推、不用危险 git 操作；
- **不允许静默改变行为**：任何"权宜之计"先说明再动。

## 4. 可追溯：让每条结论都能回到源头

一个人做久了最大的敌人是"忘了为什么这么改"。所以做了三层记录：

| 层 | 内容 |
|---|---|
| **会话块** | 每次工作一个块：做了什么、改了哪些文件、**提交短哈希**、遗留问题 |
| **编号事实** | 71 条 `F-####`：根因 / 否证清单 / 接口契约，字段含重要度、标签、`[ref: 文件]` |
| **专题日志** | 每个疑难问题一篇：现象 → 排查路径（含被排除的假设）→ 根因 → 修法 → 验证数据 → 代价 |

效果：**任何一条性能数字或根因，都能在几秒内定位到日志字段或提交**。面试/评审被追问"这个数哪来的"时，这一层就是底气。

## 5. AI 出错被纠正的三类典型（真实发生过）

> 这三类的共同点：**不是 AI 写错代码，而是它把"不确定"说成了"确定"**。

### 5.1 "观测缺失"被当成"执行缺失"

AI 因为日志里没看到某一行，断言"某条代码路径没被执行"，并给出完整因果链。
**真因是日志系统自身的 tag 槽位不够**（注入了 12 个 tag，槽位只有 10 个，最后两个被静默丢弃）。
反证靠三件事：槽位算术、主机测试必然会打印的那几行、以及日志里**另一个 tag** 打印的同一事件。
⇒ 教训固化为一条纪律：**"日志里没有" ≠ "代码没执行"**，先查过滤器 / 槽位 / 编译开关三层。

### 5.2 "配置看起来改了"其实没生效

AI 连续多轮汇报某个构建开关的性能数字，但那个开关**在构建系统里根本没有声明**（只存在于 C 头文件的
`#ifndef` 默认值里）⇒ 传进去的宏只是建了个**没人读的缓存变量**，从未进编译器。
揭穿靠**产物级证据**：`compile_commands.json` 里没有对应 `-D`、`boot.map` 里段的尺寸对应的是另一种配置。
⇒ 纪律：**构建命令 ≠ 生效配置，只信产物**。

### 5.3 "漂亮的算术"代替因果

AI 给出一个很精确的算式（余数恰好等于一个对齐边界），把它当成根因。
下一份板上日志显示真因完全是另一回事（中断被屏蔽导致状态机等不到完成），那个余数只是**伴生巧合**。
⇒ 纪律：**根因要能给出机制，不能只因算术吻合**。

### 还有一类：AI 为了让症状消失而改行为

被明确制止过：**"不要想着掩盖，优先查根因；需要退而求其次时先说，不允许静默改变行为。"**
后来真正的修法是机制层面的修复，而不是"让现象看不见"。

---

## 6. 一句话总结

> **AI 做执行，人定判据与纪律。**
> 工具链选对（现代化编辑器 + CMake + 可编程调试/仿真/串口通道）只是让 AI **能进来**；
> 真正让它**有用而不危险**的，是任务书、判据、独立审计与可追溯的记录。
